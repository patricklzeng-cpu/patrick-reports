02 / Problem frame

三个动机，三个待证假设

视频的直觉很强：模型各有长短、原生 harness 有专门适配、昂贵模型不该包办所有阶段。问题是，直觉要变成收益，必须跨过交接损耗与验证成本。

视频主张

按能力分工

强模型做计划或把关，执行交给更合适的模型，理论上能发挥互补优势。

TEST → 同题一次通过率 + reviewer 真阳性
待验证

按价格分层

把大量执行 token 交给便宜模型，可能降低模型费用；但复核、重试和上下文复制也会涨价。

TEST → 被验收任务的总成本
产品能力

保留原生 harness

Claude Code、Codex 等继续运行在真实终端中，由 Herdr 负责寻址、I/O、状态与持久化。

BOUNDARY → 控制面，不是共享记忆
任务形状单强 Agent多 Agent判定依据
强顺序依赖、小改动优先协作税偏高handoff 多于可并行工作
可独立探索的多方案可做基线适合试点并行收益可测、聚合规则明确
高风险变更 + 独立审核可行角色分离有价值reviewer 有清晰 gate 与证据
上下文高度隐性更安全容易丢语义除非先冻结共享契约
重复批处理、接口固定视规模并行度高共享 schema + 幂等写入
关键反转：“更多 Agent”不是架构目标。目标是让最少数量的独立认知路径，在可追踪交接与明确验收下，改善一个事先选定的主指标。
03 / Product anatomy

Herdr 到底解决哪一层？

把界面结构和自动化原语分开看，就不会把“能发送 prompt”误读成“自动理解上下文”。

SESSION后台 server · detach 后继续运行
WORKSPACE一个项目级容器
TAB一个工作视角
PANE真实终端 + 进程
AGENT被识别的 coding agent
layout

创建 workspace、tab 和 pane 拓扑。它只负责“在哪里运行”。

pane

对原始终端运行命令、发键、读输出、等待文字。普通进程也能用。

agent

按名称或 pane 控制已识别 agent，并读取 working / blocked / done / idle / unknown。

socket

本地 API 暴露读、写、prompt、wait 与事件订阅，供脚本或另一个 agent 调用。

提供

会话持久化

Detach 不结束 agent；重新 attach 后继续看真实终端与状态。

提供

可寻址控制

按 agent 名或 pane ID 发送任务、读输出、等待状态，并组织布局。

不提供

正确性证明

done / idle / unknown 不是验收；测试、diff、artifact 与独立 reviewer 才是。

04 / Quick start

十分钟建立可信控制面

命令取自 2026-08-11 官方文档快照。先验证单 agent 会话，再装集成，最后才上编排。

01

安装与启动

macOS / Linux 可用官方安装器；Homebrew 用户可直接安装。启动后 Herdr 会创建或连接默认后台 session。

brew install herdr
herdr
02

确认心智模型

为项目建 workspace；tab 是工作视角，pane 是真实终端。先 detach / attach 一次，确认进程持久化符合预期。

# 在任意项目目录启动
herdr
# detach 后 agent 仍继续运行
03

安装目标 agent 集成

Claude Code 与 Codex 的 hook 提供原生 session identity；其 lifecycle 状态仍主要来自 screen manifest。

herdr integration install claude
herdr integration install codex
herdr integration status
04

用最小 reviewer 配方验收

先在已有 shell pane 启动 reviewer，再 prompt、wait、read。把输出写入文件作为 alternate-screen 丢历史时的回退。

herdr agent start reviewer --kind codex --pane w1:p2
herdr agent prompt reviewer "Review the current diff" --wait --timeout 120000
herdr agent read reviewer --source recent-unwrapped --lines 120
不要跳过：在目标 CLI 版本、主题、语言和权限弹窗下测试 blocked / idle / done / unknown。状态检测是可用性信号，不是任务正确性证据。

视频观察

审核不是一次性动作

ASR 记录中 reviewer 提出多个问题，planner 修订后继续回传；视频称经过多轮交互才通过。这说明真正的成本单位是“整个闭环”，不是单次调用。

仪表盘补强

把 reviewer 与 verifier 分开

计划审核判断“方案是否足够好”；验收门判断“产物是否实际满足标准”。两者合并会让同一认知路径既出题又判卷。

可复用的最小编排：Planner 只写计划；Reviewer 只给带证据的 blocking / non-blocking 反馈；Executor 只按冻结计划改动；Verifier 只读产物和测试结果。每一步都返回下一步可消费的结构化对象。
06 / Contract before agents

先写交接，再启动 Agent

试着填入三项。准备度不是“质量分”，而是检查任务有没有可消费的输入、明确输出和可验证成功条件。

HANDOFF READINESS
0%

输入不可隐式

不说“看一下项目”；给确切路径、当前状态、可信来源和禁止触碰的边界。

输出必须可消费

不说“给个方案”；约定 JSON / Markdown / diff / 文件路径以及下一角色如何读取。

成功必须可判定

不说“做完告诉我”；指定测试、阈值、证据、失败升级与最大循环次数。

循环保险丝：Planner ↔ Reviewer 最多 N 轮；仍不通过就升级给人或改写任务。无限 self-refinement 不是严谨，是失控的预算。

10 / Tier-4 anti-mapping

本地能力没有自动解决什么？

五张卡使用严格四态：机制级缓解、类比、部分缓解、未覆盖缺口。本页 3/5 为非完全缓解，避免“有个 skill 就算问题解决”。

机制级缓解

交接 schema 漂移

`parallel-subagent-shared-contract` 与 `task-decomposition` 在派工前冻结输入、输出和成功条件，直接作用于接口错位。

看 3C 检查器 →
机制级缓解

过程不可见

`cross-agent-observability` 记录依赖、状态、成本与 handoff，使失败至少有 trace 可回放。

看图谱关系 →
部分缓解

失败责任归因

有 trace 仍不等于能找出决定性错误步骤。ICML 基准显示自动归因远未解决，需要证据指针和人工审计。

外部反证 ↗
部分缓解

模型—任务最优路由

`llm-protocol-router` 可按规则路由；但 `hybrid-llm-router` 仅 scaffold，没有真实成本/质量回归数据。

用 A/B 建证据 →
未覆盖缺口

共享语义与冲突消解

Herdr 传 prompt 和终端输出，不提供共享世界模型、自动事实合并、冲突仲裁或全局正确性证明。

协作税研究 ↗
采用门槛：如果团队不能写出“哪类任务可并行、交接对象是什么、失败怎么升级、最终由什么验收”，那就先不要增加 Agent。Herdr 会把混乱运行得更持久，但不会替你定义秩序。
