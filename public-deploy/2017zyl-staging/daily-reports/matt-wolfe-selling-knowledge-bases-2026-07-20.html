[00:00-03:45] #01 机会:无聊的知识库反而赢了 The Boring Knowledge Base That Actually Works

Matt 开场讲 Sarah 所在的大型 AI 硬件公司(做推理芯片,服务多家十亿美元客户)刚发了一篇 blog 介绍内部知识库。他们没有展示 obsidian 图表、没有 3D 大脑漂浮动画,而是展示了一个可靠的数据摄入管道。Slack 每条对话、Confluence wiki、GitHub 仓库、自定义数据库全部吸入,让公司里任何人能问业务问题。Matt 借此批评当下花哨的"第二大脑"工具:知识库应该无聊、可靠、稳健、能从多源摄入数据并吐出准确答案 — 这才是企业愿意付费的价值。 Matt opens with Sarah's massive AI hardware company (inference chips, billion-dollar clients). They just blogged about their internal knowledge base — no obsidian graphs, no 3D brain-in-a-tube, just a reliable data ingestion pipeline. Every Slack conversation, Confluence wiki, GitHub repo, custom database — all sucked in, so anyone in the company can ask business questions. Matt uses this to critique today's flashy 'second brain' tools: a knowledge base should be boring, reliable, robust, ingest from multiple sources, and spit out accurate answers — that's what enterprises pay for.
  • AI 硬件公司内部知识库:Sarah 团队建了一个能问业务问题的 queryable KB
  • 数据源覆盖:Slack(全公司历史对话) + Confluence/Wiki + GitHub(代码/issue/PR) + 自定义数据库(CRM/ERP) + 网表 PRM docs
  • vs 花哨工具:Obsidian 知识图谱 / 3D 大脑漂浮动画 — 视觉噱头,可靠性差
  • 核心价值 = 数据摄入管道的准确性和可靠性,不是 UI 美观
  • AI hardware company internal KB: Sarah's team built a queryable KB for business Q&A
  • Data source coverage: Slack (all historical chats) + Confluence/Wiki + GitHub (code/issues/PRs) + custom DB (CRM/ERP) + netlist PRM docs
  • vs flashy tools: Obsidian graphs / 3D brain-in-a-tube — visual gimmick, unreliable
  • Core value = accuracy + reliability of data ingestion pipeline, not UI polish

[03:45-08:00] #02 技术栈:Quivr + Postgres pgvector + GPT-4o Tech Stack: Quivr + Postgres pgvector + GPT-4o

Matt 给出他认为最可靠的 5 件套技术栈。核心是开源项目 Quivr(开源 RAG 系统,无聊但好用)。向量数据库用 Postgres + pgvector 扩展(无聊但已经到处在跑)。Embedding 模型用 OpenAI text-embedding-3-small(性价比最优)。LLM 用 GPT-4o — Matt 解释为什么不用 Claude/开源:不是模型问题,是数据摄入管道问题 — 摄入管道拉胯的话,什么 LLM 都救不了,所以先调摄入,再选 LLM。 Matt gives his go-to reliable 5-piece stack. Core = Quivr (open-source RAG, boring but works). Vector DB = Postgres + pgvector extension (boring, probably already running somewhere). Embedding = OpenAI text-embedding-3-small (best cost/perf). LLM = GPT-4o — Matt explains why not Claude/open-source: the problem is the data ingestion pipeline, not the model. If ingestion is crap, no LLM saves it. Tune ingestion first, LLM choice second.
  • Quivr:开源 RAG 框架,'无聊但好用' — 不做花哨可视化,专注多源摄入 + 准确回答
  • Postgres + pgvector:无聊但到处在跑的向量数据库,无需额外部署
  • OpenAI text-embedding-3-small:性价比最优的 embedding 模型
  • LLM 选 GPT-4o:指令遵循强、成本合理 — 但 Matt 强调 LLM 选择不是关键
  • 优先级反转:80% 时间调数据摄入管道,20% 选 LLM
  • Quivr: open-source RAG framework, 'boring but works' — no fancy visualization, just multi-source ingestion + accurate answers
  • Postgres + pgvector: boring but ubiquitous vector DB, no extra deployment
  • OpenAI text-embedding-3-small: best cost/perf embedding model
  • LLM = GPT-4o: strong instruction-following, reasonable cost — but Matt emphasizes LLM choice is NOT the bottleneck
  • Priority inversion: 80% time on data ingestion pipeline, 20% on LLM

[08:00-18:30] #03 构建实战 + 5 个数据源优先级 Build Walkthrough + Data Source Priorities

Matt 演示完整 build 流程。Step 1:clone Quivr + 配环境变量(OpenAI key / DB URL / Slack token)+ 跑迁移 + 启服务。Step 2:接数据源 — 这是 80% 工作量。Matt 给出 5 个优先级:(1) Slack(全公司历史对话,流失最快的知识);(2) Wiki/Confluence(经常过时,需谨慎摄入);(3) GitHub(issue/PR/comment);(4) 自定义数据库(SQL 查询 + chunk);(5) 杂项(PDF/Google Docs/Notion)。每源都有自己的连接方式:Slack API 拉历史 + 过滤 noise / Firecrawl 爬 wiki / GitHub API 拉 issue/PR / 自定义 SQL connector。最后一步是调参:chunk size / overlap / embedding / LLM 选型 — 用一组 test query 反复迭代。 Matt demos the full build. Step 1: clone Quivr + env vars (OpenAI key, DB URL, Slack token) + migrations + start server. Step 2: connect data sources — 80% of the work. Matt's 5-priority list: (1) Slack (all company history, fastest-lost knowledge); (2) Wiki/Confluence (often stale, ingest carefully); (3) GitHub (issues/PRs/comments); (4) Custom DBs (SQL query + chunk); (5) Misc (PDFs/Google Docs/Notion). Each has its own connector: Slack API + filter noise / Firecrawl crawl wiki / GitHub API + filter / custom SQL connector. Final step: tune — chunk size / overlap / embedding / LLM via a test-query loop.

  • Wiki 连接器:Firecrawl 爬 → extract content → chunk + ingest
  • GitHub 连接器:API 拉 issue/PR/comment → filter → ingest
  • 调参闭环:用 test query 反复迭代 chunk size / overlap / embedding / LLM 直到答案准确
  • Step 1-4: Quivr setup — git clone → env vars → migrations → start server
  • Data source priority P1=Slack, P2=Wiki/Confluence, P3=GitHub, P4=Custom DB, P5=Misc (PDF/Notion/Google Docs)
